GPU is well known for accelerating parallelizable operations such as matrix multiplication. We consider how it can process multiple jobs simultaneously from a high level, and give a few specific examples.

Hardware Involved in GPU Computations

We first start with the physical hardware involved in GPU computations, roughly in the order that the data travels:

  • SSD Storage (Solid-state Drive) is where datasets and model weights live permanently.
  • DDR RAM (Double Data Rate) is system memory dedicated to the CPU. The CPU reads the data from SSD and loads it into RAM.
  • PCI Bus (Peripheral Component Interconnect) passes the data from RAM to VRAM.
  • VRAM (Video Random Access Memory) is a specialized type of memory dedicated to the GPU. HBM is one type of VRAM.
  • SRAM (Static Random Access Memory) is known as the GPU cache. The GPU pulls small tiles of data from VRAM into it for performing operations. SRAM is usually very small, e.g. 228 KB for one SRAM.
  • Registers: a register is the fastest and smallest memory unit in a GPU. One register is dedicated to one thread (while one thread could have many registers). There are different types of registers, such as fetching registers and accumulator registers.

Thread, Compute Core, and Streaming Multiprocessor

Thread: a sequence of instructions to complete one task. E.g. to compute a $1024 \times 1024$ matrix, a tiny $8 \times 8$ sub-block of the final matrix is assigned to a worker. The sequence of instructions to finish this task is a thread. Roughly: load data from SRAM to registers, multiply the numbers, and get the results back to registers.

Compute core: a single unit for performing mathematical operations.

Streaming Multiprocessor (SM): one GPU has many SMs (e.g. NVIDIA H100 has 132 SMs). Each SM has many compute cores, its own SRAM and registers.

High Level Overview of How a GPU Works

Putting the pieces together, this is how a GPU would work:

Notes about the picture:

  1. The CPU reads the data and model from SSD into DDR RAM, and then it is read into VRAM through the PCI bus.
  2. Parallel operations, such as matrix multiplication, are divided into smaller, independent sub-tasks (e.g. calculating a single 8x8 final matrix block) and distributed across available Streaming Multiprocessors (SMs). If the number of tasks exceeds the number of SMs, some SMs must process multiple assignments. This creates a bottleneck: for example, if we distribute 133 tasks across 132 SMs, one SM has to process two tasks. Because the entire operation cannot finish until the slowest SM completes its work, the other 131 SMs will sit idle. As a result, the total execution time is roughly the same as if we were running 264 tasks. This is why in deep learning, the number of batch sizes, hidden dimensions, attention heads, and embedding sizes, are almost always powers of 2 (32, 64, 128, 256), because 64 would take almost the same time as 60.
  3. The corresponding data will be read from VRAM into the SRAM of that SM. Note that SRAM is usually very small, e.g. 228 KB, so the complete working set for a single thread block often cannot fit simultaneously. Consequently, the data must be partitioned and streamed into SRAM iteratively through memory tiling.
  4. Within the SM, operands are fetched from SRAM (shared memory) into the local register file. The compute cores perform the arithmetic operations and write the partial results into dedicated accumulator registers. These accumulators maintain the running sums locally, avoiding costly memory round-trips by holding the cumulative values in-place until the thread fully completes its assigned matrix tile.
  5. Once the final matrix block is computed, it is written back to SRAM from the accumulator registers, and then written back to VRAM.

A Specific Example: Matrix Multiplication

In order to understand how GPU works better, let us consider a concrete example. Say we have matrices $A \in \mathbb{R}^{1024 \times 1024}$ and $B \in \mathbb{R}^{1024 \times 1024}$, and we want to compute $AB = C$ in the GPU.

Step 1: Output division

The GPU's scheduler looks at the $1024 \times 1024$ matrix $C$ and divides it into a grid of smaller output blocks (e.g. $128 \times 128$ blocks). Each block will be assigned to one SM.

Step 2: Loading tiles (from HBM to SRAM)

In order to compute the $128 \times 128$ block, the SM needs the corresponding 128 rows from $A$ and 128 columns from $B$. However, SRAM might not fit all of this data. Instead, the SM loads a thin slice from HBM, for example a $128 \times 32$ slice from $A$ and a $32 \times 128$ slice from $B$. The SM reads one slice from $A$ and from $B$ at a time.

Step 3: Register allocation (from SRAM to registers)

One thread will get assigned to compute an $8 \times 8$ small block. The thread will reserve multiple accumulator registers and private registers (fetching registers).

Step 4: Computation

The thread reads data from the fetching registers and adds the results directly into the accumulator registers.

Step 5: Sliding the tile

Once the thread exhausts the data in the current SRAM slice, the SM slides the window, feeding the next slices from $A$ and $B$. Crucially, the accumulator registers hold the running sums until all slices are used.

Step 6: Write back (accumulator registers → SRAM → HBM)

Once the sliding window reaches the end, the accumulator registers hold the final results. They will be written back to SRAM and then to HBM.

Some ML Observations

Given our understanding of GPU architecture (HBM, SRAM, and SM execution), here is some of the examples about how these hardware influences machine learning in practice.

1. A batch often takes almost the same time as a single sample

Processing a small batch (e.g., 32 samples) often takes nearly the same latency as processing a single sample because the operation is dominated by weight loading, not computation itself. To execute a forward pass, the GPU must stream the model's weights from HBM into SRAM. For a single sample, the arithmetic intensity (FLOPs per byte) is extremely low. By processing a batch, the GPU loads those massive weight matrices into SRAM once and reuses them across all 32 inputs. Because the Tensor Cores perform the actual matrix math near-instantaneously, this computation time is completely hidden behind the HBM-to-SRAM memory transfer. By processing a batch, rather than a single sample, we achieve significantly higher throughput with almost zero latency penalty.

2. What it means to be memory-bound (e.g., LLM inference)

A workload is "memory-bound" when the GPU's compute cores spend the majority of their computational units idling, waiting for data to travel from HBM to SRAM. Autoregressive LLM inference (the generation phase) is an example. Generating a single new token relies on matrix-vector multiplication, meaning the entire model must be fetched from HBM to SRAM just to perform a tiny amount of math. Because modern GPU HBM bandwidth (the data pipe) is orders of magnitude slower than its peak TFLOPs (the math engine), the bottleneck is entirely physical data transport rather than mathematical execution.
