Huffman Encoding

Computer Science

A concise handwritten version of this note is available as a PDF.

Every time you unzip a file and get back exactly what you put in, something slightly magical has happened: the file was stored using fewer bits than the original, yet nothing was lost. How is that even possible? Huffman encoding is one of the classic answers, and it (or a close cousin) is still sitting inside zip files, JPEG, and MP3 today.

Suppose we want to send a message — say the word "Shannon" — from our computer to a robot. The encoder turns the message into bits (e.g. S → 100, h → 001, a → 000, ...), the bits travel over the wire, and the decoder on the robot's side recovers the message exactly. That "exactly" is what makes it lossless — i.e. message = decompress(compress(message)). The problem Huffman encoding tries to solve is then:

How do we use as few bits as possible to encode a message losslessly?

The Naive Way: Equal-Length Codes

If we have 2n unique symbols, a naive way is to give each symbol an equal-length binary string. With four symbols a, b, c, d:

a → 00    b → 01    c → 10    d → 11

But what if we know the frequencies of symbols in the message? Say:

a: 50%    b: 25%    c: 12.5%    d: 12.5%

The intuition is immediate: if a appears more often, we may want to use fewer bits to represent it. This is the same trick Morse code played long before computers — "e" gets a single dot.

What are we actually minimizing? The total length is n (number of symbols) times the expected length per symbol:

E = p(a)·L(a) + p(b)·L(b) + p(c)·L(c) + p(d)·L(d)

With the equal-length code, E = 0.5×2 + 0.25×2 + 0.125×2 + 0.125×2 = 2 bits per symbol. Can we do better?

The Catch: You Can't Just Shorten Codes

Here's the difficulty: we want to use as few bits as possible, but we want lossless compression, so we can't be too greedy. Say we cut a's code from 00 down to 0:

a → 0    b → 01    c → 10    d → 11

Now how do we decode 01011? It could be 0|10|11 → acd, or it could be 01|0|11 → bad. Ambiguous — the compression is no longer lossless.

This gives us the key requirement: if a symbol takes bit string b₁b₂...bₖ, then no other symbol's code can start with the whole b₁b₂...bₖ (e.g. b₁b₂...bₖ0 is not allowed). In other words, a symbol's code cannot be a prefix of any other symbol's code — this is called a prefix code.

A First Attempt: Shannon-Fano Coding

Shannon-Fano coding builds a prefix code top-down:

  1. Rank symbols by probability from low to high: c (12.5%), d (12.5%), b (25%), a (50%).
  2. Divide the sum of probabilities into half — one half goes left, one half goes right.
  3. Repeat within each half until every branch has a single symbol.
              (root)
             0/    \1
        {c,d,b}     a          ← 50% | 50% split
        0/    \1
    {c,d}      b               ← 25% | 25% split
    0/  \1
    c    d

a → 1    b → 01    c → 000    d → 001

Notice in this tree, no symbol is a prefix of another — every symbol sits at a leaf. To decode any bit string, simply walk down the tree: 0 means go left, 1 means go right, and when you hit a leaf you emit that symbol and jump back to the root. So 001|1|01|001 decodes unambiguously to c a b d.

And the expected length improves:

E = 1×0.5 + 2×0.25 + 3×0.125 + 3×0.125 = 1.75

We went from 2 bits to 1.75 bits per symbol, and we can still decode exactly. Nice. Are we done?

Why Shannon-Fano Is Not Optimal

It is quite surprising to me when I first know that Shannon-Fano — Shannon's own scheme! — is not optimal in general. To construct an optimal encoding, let's stare at the tree again and make two observations.

Observation 1: the number of bits for a symbol equals its depth in the tree. So for any two symbols a and b, if p(a) < p(b), then in an optimal tree we must have depth(a) ≥ depth(b). In particular, if p₁ ≤ p₂ ≤ ... ≤ pₖ, the symbols with the lowest probabilities must be on the bottom layer of the tree — and we can always arrange the two smallest, p₁ and p₂, to be siblings there.

Observation 2: the expected length equals the sum of probabilities at each internal node of the tree. In our example: 50% + 50% + 25% + 25% + 12.5% + 12.5% = 1.75 — exactly E. Why? A symbol at depth k appears in (i.e. contributes its probability to) k nodes on its way down.

Put together, these give a recurrence for the optimal expected length L:

L(p₁, p₂, ..., pₖ) = p₁ + p₂ + L(p₁+p₂, p₃, ..., pₖ),   where p₁ ≤ p₂ ≤ ... ≤ pₖ

Read it out loud: merging the two least likely symbols costs us p₁ + p₂ (they each get one bit deeper), and the rest of the problem is the same problem, one symbol smaller — the merged pair now acts as a single symbol with probability p₁ + p₂. That's the whole algorithm. Huffman builds the tree bottom-up by repeatedly merging the two least likely symbols, whereas Shannon-Fano splits top-down and can make splits that no rearrangement can fix.

A Worked Example Where Huffman Wins

Take five symbols with these probabilities:

D: 0.15    E: 0.16    A: 0.17    C: 0.17    B: 0.35

Step 1: merge the two smallest, D and E → node DE with 0.31. Now we have A (0.17), C (0.17), DE (0.31), B (0.35).

Step 2: merge A and C → node AC with 0.34. Now we have DE (0.31), AC (0.34), B (0.35).

Step 3: merge DE and AC → node DEAC with 0.65. Now we have B (0.35), DEAC (0.65).

Step 4: merge DEAC and B → the root. The finished tree:

            (root)
           0/    \1
       DEAC       B          B → 1
       0.65      0.35        D → 000
      0/    \1               E → 001
    DE       AC              A → 010
   0/ \1    0/ \1            C → 011
   D   E    A   C
 0.15 0.16 0.17 0.17

Expected length, using Observation 2 (or just counting depths):

L = 0.35 + 0.65×3 = 0.35 + 1.95 = 2.3

Now compare with Shannon-Fano on the same probabilities. Ranking D, E, A, C, B and splitting the halves top-down gives B → 11, D → 000, E → 001, A → 01, C → 10, with:

L = 2×0.35 + 3×0.15 + 3×0.16 + 2×0.17 + 2×0.17 = 2.31

Here we are: 2.3 vs 2.31. The gap is tiny in this example, but it's real — and Huffman is provably optimal among symbol-by-symbol prefix codes, while Shannon-Fano is not. Two least-likely symbols merged at a time, all the way up, and you cannot do better.

Summary

  • Lossless compression means message = decompress(compress(message)) — the decoder recovers the message exactly.
  • The quantity to minimize is the expected code length per symbol, E = Σ p(s)·L(s); frequent symbols should get short codes.
  • The key constraint is the prefix property: no symbol's code can be a prefix of another's, otherwise decoding is ambiguous.
  • Codes live on a binary tree: code length = depth, and expected length = sum of probabilities over the tree's internal nodes.
  • Huffman's move: repeatedly merge the two least likely symbols, since L(p₁,...,pₖ) = p₁ + p₂ + L(p₁+p₂, p₃,...,pₖ). This is optimal; top-down Shannon-Fano is not.

My Take

What I love about this note is how far you get with just two observations about a tree. The recurrence L(p₁,...,pₖ) = p₁ + p₂ + L(p₁+p₂,...) looks almost too simple to be the whole story, and yet it turns "find the optimal code" — a search over exponentially many trees — into a greedy loop you could implement with a heap in ten lines. It's also a nice reminder that the obvious top-down approach (Shannon-Fano: keep splitting in half, feels so natural) can be quietly wrong, while the right answer works bottom-up from the least important symbols. The caveat worth remembering: Huffman is only optimal when you must give each symbol a whole number of bits. If your probabilities aren't powers of 1/2, arithmetic coding can squeeze out a bit more — but that's a note for another day.
