FlashAttention

LLM

A concise handwritten version of this note is available as a PDF.

FlashAttention is one of those ideas that seems obvious in hindsight but is genuinely clever. The key insight is that standard attention wastes memory by materializing the full N x N score matrix, but you can compute the exact same result block by block without ever storing it. The trick that makes this work is an online softmax update rule.

Standard Attention Recap

Recall that standard attention computes:

R = Softmax(Q K^T / sqrt(d)) V

Here R is the output matrix. The problem is that computing the full Q K^T matrix requires O(N^2) memory where N is the sequence length. For long sequences, this intermediate matrix is enormous and must be read/written to slow GPU high-bandwidth memory (HBM).

The FlashAttention Idea: Block-wise Computation

FlashAttention divides Q, K, and V into b small blocks, each containing t elements (queries, keys, or values):

Q = [Q_1, Q_2, ..., Q_b]      (b blocks of queries, each of size t)
K = [K_1, K_2, ..., K_b]      (b blocks of keys)
V = [V_1, V_2, ..., V_b]      (b blocks of values)

The output R can similarly be partitioned into blocks:

R = [R_1, R_2, ..., R_b]

The key point is that FlashAttention computes each output block R_1, R_2, ..., R_b separately, and within each output block, it builds the result gradually by streaming through the K and V blocks one at a time.

Gradual computation of R_1

Taking R_1 as an example (all other R_i are updated similarly), FlashAttention computes it in b steps:

Step 1:  R_1^(1) = Softmax(Q_1 (K_1^T) / sqrt(d)) (V_1)

Step 2:  R_1^(2) = Softmax(Q_1 (K_1^T  K_2^T) / sqrt(d)) (V_1)
                                                             (V_2)

Step 3:  R_1^(3) = Softmax(Q_1 (K_1^T  K_2^T  K_3^T) / sqrt(d)) (V_1)
                                                                    (V_2)
                                                                    (V_3)
  ...

Step b:  R_1^(b) = Softmax(Q_1 (K_1^T ... K_b^T) / sqrt(d)) (V_1)
                                                               ( : )
                                                               (V_b)

After b steps, R_1^(b) = R_1, which is what we want in the end. The critical question is: how do we update from R_1^(i) to R_1^(i+1) efficiently without recomputing everything from scratch?

Efficient Incremental Updates

Let us take one query from Q_1 as an example. Without loss of generality, denote it as q_1, and denote its output after step i as r_1^(i+1).

Expanding the output at step (i+1)

After processing through the (i+1)-th K and V blocks, the output for query q_1 is:

r_1^(i+1) = Softmax(q_1^T (K_1 ... K_(i+1)t) / sqrt(d)) (V_1  )
                                                            ( :   )
                                                            (V_i+1)

Since the (i+1)-th step has seen keys from blocks 1 through (i+1) (a total of (i+1)t keys), and each block has t values, we can write this out explicitly:

         exp(q_1^T k_j / sqrt(d) - s^(in))
r_1^(i+1) = SUM_j  --------------------------------  *  v_j
         SUM_j' exp(q_1^T k_j' / sqrt(d) - s^(in))

Here s^(in) is the maximum of q_1^T k_j / sqrt(d) across all j in blocks 1...(i+1). This is the "max trick" subtracted for numerical stability (it does not change the result since it cancels in the softmax ratio, but prevents overflow in the exponentials).

We use v_j (small v) to denote the value corresponding to key k_j.

The decomposition

The key mathematical insight is that we can split the sum in both the numerator and denominator into two parts: the contribution from blocks 1...i (which we already computed) and the new contribution from block i+1:

         SUM_{j=1}^{it} exp(q_1^T k_j / sqrt(d) - s^(in)) v_j
         +  SUM_{j=it+1}^{(i+1)t} exp(q_1^T k_j / sqrt(d) - s^(in)) v_j
r_1^(i+1) = ----------------------------------------------------------
                SUM_{j=1}^{(i+1)t} exp(q_1^T k_j / sqrt(d) - s^(in))

This can be further rewritten by separating the two parts:

              SUM_{j=1}^{it} exp(q_1^T k_j/sqrt(d) - s^(i))
r_1^(i+1) =  ------------------------------------------------  *  [previous weighted sum]
              SUM_{j=1}^{(i+1)t} exp(q_1^T k_j/sqrt(d) - s^(in))

              SUM_{j=it+1}^{(i+1)t} exp(q_1^T k_j/sqrt(d) - s^(in))
           +  -------------------------------------------------------  *  [new block weighted sum]
              SUM_{j=1}^{(i+1)t} exp(q_1^T k_j/sqrt(d) - s^(in))
The second term depends only on block K_{i+1} and V_{i+1}. At each step, the running denominator sum can be updated incrementally, and the new block's contribution is computed fresh. This is what makes FlashAttention work without storing the full N x N attention matrix.

What Gets Updated at Each Step

At each step when processing a new K/V block, we maintain and update:

  • The running sum of exponentials (denominator): this accumulates across all blocks seen so far and can be updated by simply adding the new block's contribution (with appropriate rescaling when the running max changes)
  • The running weighted numerator: the sum of exp(score) * v terms, which is similarly updated by rescaling the old sum and adding the new block's terms
  • The running max s^(in): updated as the max of the old max and the new block's max, needed for numerical stability

Why This Matters: Memory Efficiency

The standard attention algorithm materializes the full N x N attention score matrix in HBM. FlashAttention avoids this by:

  • Only ever working with blocks of size t x t in fast on-chip SRAM
  • Never writing the full attention matrix to slow HBM
  • Achieving the same exact result (not an approximation) through the incremental update scheme described above

Here we are: FlashAttention is IO-aware -- it is designed around the GPU memory hierarchy. By keeping blocks small enough to fit in SRAM, it reduces the number of reads/writes to HBM, which is the actual bottleneck for attention computation on modern hardware. The speedup is substantial -- 2-4x wall-clock time on typical sequence lengths.

Summary

  • FlashAttention tiles Q, K, V into blocks and uses an online softmax trick (running max + running sum of exponentials) to compute exact attention incrementally -- no approximation involved
  • It is IO-aware: blocks fit in SRAM, avoiding repeated reads/writes to slow HBM, making it super fast in practice (2-4x speedup)
  • The downside is implementation complexity -- the kernel is highly hardware-specific, and custom backward passes are needed for training; not something you casually reimplement
