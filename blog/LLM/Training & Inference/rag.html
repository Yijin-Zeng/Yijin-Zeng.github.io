Retrieval-Augmented Generation (RAG)

LLM

A concise handwritten version of this note is available as a PDF.

RAG is one of the most widely used techniques for making LLMs actually useful in real world. Instead of relying solely on what the model memorized during training, RAG fetches relevant contexts at query time and inject it into the prompt.

1. Why Do We Need RAG?

1.1 Give LLMs Knowledge They Did Not Learn

A model trained with a knowledge at certain point (say 2022) simply cannot answer questions about events after that date. For example: "What is the current marathon world record as of 2026?" RAG solves this by fetching up-to-date contexts at query time and injecting it into the prompt.

1.2 Dealing with Long Context

We cannot always just paste all relevant information directly into the prompt. There are several practical reasons:

  1. Limited context window -- even modern models have a finite number of tokens they can process at once.
  2. Latency -- transformer self-attention has O(n^2) complexity in the sequence length, so longer prompts are significantly slower.
  3. Memory / lost-in-the-middle -- models tend to focus on the beginning and end of long contexts, often missing information in the middle.

1.3 Data Security

  • Keep data internal -- sensitive documents can be saved locally; they are only retrieved and inserted into prompts at inference time.
  • Machine unlearning is hard -- once a model has been fine-tuned on data, removing that knowledge could be very hard. With RAG, we can simply delete the document from the vector store.

2. How Does RAG Actually Work?

The pipeline has two main phases: an offline indexing phase (which can be pre-processed) and an online query phase.

Offline Indexing Phase

Internal Documents
       |
       v
    [ Split ] into different chunks
       |
       v
    [ Embedding Model ] encodes each chunk
       |
       v
    [ Vector Database ] stores all chunk embeddings

Online Query Phase

User Query
       |
       v
    [ Embedding Model ] encodes the query
       |
       v
    [ Retriever ] finds top-k similar chunks from vector DB
       |
       v
    [ Generative Model ] receives query + retrieved context, generates response

Notes

  1. Noarmlly, the same embedding model is used for both the user query and the document text -- this ensures they live in the same vector space.
  2. The retriever is normally just cosine similarity, but can be more complex -- e.g., combining embedding-based search with keyword search (BM25), or using a learned re-ranking model.
  3. The user query and retrieved context are typically concatenated in the prompt as follows:
system: [system prompt]
context: [retrieved context]
user: [user query]

3. Chunking Strategies (Split)

How we split documents into chunks has a major impact on retrieval quality. There are differen ways to do this, from naive to more sophisticated:

3.1 Fixed-Size Sliding Window

The simplest method: split the document into fixed-size windows (possibly with overlap).

|---- chunk 1 ----|
          |---- chunk 2 ----|
                    |---- chunk 3 ----|  ...
Problem: breaks logical chains of thought. A sentence or argument may be split across two chunks.

3.2 Split by Structure

Split at natural boundaries -- paragraphs, sections, sentences.

Problem: several different paragraphs could all be relevant to a single query, and we may miss cross-paragraph dependencies.

3.3 Semantic Chunking

A smarter approach that splits based on meaning rather than arbitrary boundaries:

  1. Take consecutive sentences: Sentence 1, Sentence 2, ... Sentence n.
  2. Embed each sentence individually: Embedding 1, Embedding 2, ... Embedding n.
  3. Compute cosine similarity between adjacent pairs: S1, S2, S3, ...
  4. Plot similarities and split where similarity drops suddenly -- this indicates a topic shift.
Similarity
  |  x  x
  |       x  x  x
  |                x     <-- sudden drop = split here
  |                  x
  +------------------------
    S1 S2 S3 S4 S5 S6 S7

This preserves semantic coherence within each chunk while placing boundaries at natural topic transitions.

3.4 Late Chunking

Late chunking takes a fundamentally different approach to preserve global context:

  1. Feed the whole document through an encoder at once, producing one embedding per token.
  2. Apply semantic chunking (as above) to determine chunk boundaries.
  3. The embedding vector for each chunk is the average of the token embeddings within that chunk.

The key point here is that because the encoder processes the entire document, each token's embedding captures its "global meaning" -- its role in the context of the whole document, not just its local window. This produces higher-quality chunk representations.

4. Efficient Embedding and Retrieval

Problem

There is a trade-off between efficiency and quality in both embedding and retrieval:

  • Latency and memory -- we want sparse or low-dimensional vectors to save storage and speed up retrieval.
  • Quality -- we want vectors that capture enough semantic meaning.

High-dimensional vectors capture good semantic nuance, but they are expensive to store and have high retrieval latency.

4.1 Solution for efficient embedding: Matryoshka Representation Learning

This technique trains embeddings so that information is concentrated in the leading dimensions. The idea is straightforward but interesting:

  • An encoder (text or image) produces a full-dimensional embedding (e.g., 1024-d).
  • During training, the model simultaneously optimizes on multiple truncation levels: first 8, 16, 32, 64, ... up to 1024 dimensions.
  • The loss is the average across all these sub-tasks.
Note: information now is dense in the first few dimensions. We can truncate the embedding to certain prefix length e.g. 32, and still get a useful representation.

4.2 Solution for efficient retrieval: Hierarchical Navigable Small World (HNSW)

Even with compact embeddings as we just described, searching through millions of vectors with brute-force cosine similarity could be slow. We can consider some naive methods for more efficient searching. For example, we could cluster all vectors into different clusters first, and then search within the cluster. While simple, this method does not produces high quaility retrieval results in practice. A widely adopted solution is HNSW, which is a graph-based approximate nearest-neighbor algorithm that achieves O(log N) search time.

The Core Architecture

  • Layer 0 (Ground Floor): extremely dense -- contains 100% of all document vectors.
  • Higher Layers (1, 2, ...): exponentially sparser along the layer.
  • Node Presence: A node is randomly assgined a layer. If a node is assigned to Layer 2, it exists on Layer 2, Layer 1, and Layer 0, i.e. all layers below.
  • Horizontal Edges Only: connections only exist between nodes on the same layer. One node connects to its top M (e.g. 10) closest nodes, e.g. measuring by cosine similarity. There are no edges connecting nodes in different layers.

The Search Phase

When a user asks a question, the query vector q navigates the graph in O(log N) time:

  1. Enter at the Top: the query q starts at a predefined entry point (e.g. choosen randomly) on the highest, sparsest layer.
  2. Horizontal Greedy search: q measures its distance to the entry point's neighbors, jumps to the neighbor with the minimum distance, and repeats.
  3. The ef List: as q searches, it maintains a dynamic running list of the top ef (e.g., 50) closest nodes it has evaluated on that layer.
  4. Local Minimum and Drop: when q can no longer find any neighbor closer than those already in its ef list, it has hit a local minimum. It stops moving horizontally and drops down one layer, using its current position (i.e. the node with minimum distance to q at this layer) as the new starting point to search.
  5. The Final Answer: steps 2-4 repeats until q hits the local minimum on Layer 0. Because Layer 0 contains all the data, the closest nodes in the final ef list are returned as Top-K retrieved chunks.
Example (n=10 vectors, M=2 neighbors, ef=2 search size):

Layer 3:  V1 ------> V2          (sparse: only 2 nodes)
              query enters here, compares d(q,V1) and d(q,V2)

Layer 2:  V1 ----> V2 ----> V3   (slightly denser)
              check neighbors, find closest

Layer 1:  V1  V2  V3  V4  V5  V6 (denser)
              more candidates to compare

Layer 0:  V1  V2  V3  V4  V5  V6  V7  V8  V9  V10 (all vectors)
              final answer: return top-K from ef list

The Insertion Phase

When embedding a new text chunk and inserting it into the graph (also O(log N) time):

  1. Initialization: randomly assign a maximum layer height for the new node (exponential decay, so very few nodes reach the top layers).
  2. Search to Insert: the new node pretends to be a search query.
  3. Wire the Edges (M connections): for every layer the new node exists on, it selects the top M closest nodes from its ef list on that layer and creates bidirectional horizontal connections.

Why is HNSW O(log N)? It is desgined to have log(N) layers (remember that the number of nodes become exponentially sparser going up the layers). For each layer, the search is (in average) constant time. Intuitivly, because at layer n-1, the node is already at the local minimum, so we might not do too much searching at layer n.
