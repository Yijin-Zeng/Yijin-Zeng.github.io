Direct Preference Optimization (DPO)

LLM

A concise handwritten version of this note is available as a PDF.

Direct Preference Optimization (DPO) is a method for aligning language models with human preferences, making them more helpful, positive, and harmless. The key insight? We can frame the entire alignment problem as a simple classification problem, without needing a separate reward model like RLHF does.

The Core Idea

In RLHF, we build a separate value model to address the credit assignment problem (figuring out which tokens deserve credit for a good response). DPO elegantly sidesteps this complexity.

Here's how DPO works:

                          winning response (y_w)
                         /
Prompt (x) --> scored by human preference
                         \
                          losing response (y_l)

For each prompt, we generate two responses — one that's preferred (winning) and one that's not (losing). These preferences come from a score model trained on human annotations. Then we compute the likelihood of each response under two models:

  • Current model: the model we're training (being optimized)
  • Reference model: a frozen copy of the model before DPO training (typically the SFT model)

The DPO Loss

The loss function is beautifully simple:

L_DPO = -log(σ(β log(π_θ(y_w|x)/π_ref(y_w|x)) - β log(π_θ(y_l|x)/π_ref(y_l|x))))

Breaking this down:

  • π_θ(y_w|x): probability of generating the winning response under the current model
  • π_ref(y_w|x): probability of generating the winning response under the reference model
  • β: controls how much we want to update the model compared to the reference
  • σ: sigmoid function

What Does Each Term Mean?

The log-ratio log(π_θ(y_w|x)/π_ref(y_w|x)) measures how much more likely the current model is to generate the winning response compared to the reference model.

Similarly, log(π_θ(y_l|x)/π_ref(y_l|x)) measures how much more likely the current model is to generate the losing response.

The difference between these two terms — log(π_θ(y_w|x)/π_ref(y_w|x)) - log(π_θ(y_l|x)/π_ref(y_l|x)) — captures the gap in preference between the winning and losing responses.

The Role of β

The parameter β controls the strength of the update:

  • If β is large, then σ(β·[...]) → 1, making the loss → 0. This means the model is already close to optimal, and we don't need large updates.
  • If β is small, the model is allowed to deviate more from the reference, enabling larger updates.

In practice, β acts as a KL penalty coefficient — it prevents the model from drifting too far from the reference distribution, which could cause the model to collapse or forget what it learned during pre-training.

DPO vs RLHF (PPO)

So how does DPO compare to the classic RLHF pipeline? Here's a side-by-side breakdown:

Aspect RLHF (PPO) DPO
Models involved 3+ models (score, value, reference, new model) 2 models (reference, new model)
Training method RL (reinforcement learning) Supervised learning
Gradient level Token level Sequence level
Learning style Online (needs to generate) Offline
Cost High Low
Performance Better (if trained stably) Lower, but framing is easier

Why DPO Is Simpler

RLHF requires:

  • Training a reward model to score outputs
  • Training a value model to estimate expected rewards at each token
  • Running online RL where the model generates outputs, gets scored, and updates itself in a loop
  • Dealing with token-level credit assignment — figuring out which tokens contributed to the final score

DPO, on the other hand:

  • Only needs a reference model (frozen) and the current model (being trained)
  • Works on pre-collected preference pairs — no need to generate outputs during training
  • Treats the problem as supervised classification — maximize the likelihood of preferred responses
  • Operates at the sequence level — no need for per-token credit assignment

When to Use DPO?

DPO shines when:

  • You have offline preference data (pre-collected winning/losing pairs)
  • You want a simpler training pipeline without RL instability
  • You're okay with slightly lower performance compared to well-tuned RLHF

RLHF (PPO) is better when:

  • You need maximum performance and can afford the complexity
  • You want online learning where the model adapts to its own outputs
  • You have the compute and engineering resources to train multiple models stably

My Take

What I find most elegant about DPO is how it reframes the problem. Instead of building separate machinery for scoring and credit assignment, it directly optimizes the policy to prefer better responses over worse ones. The simplicity is compelling — fewer models, no RL instability, and supervised learning semantics that are easier to reason about.

That said, RLHF's online nature gives it an edge when you need to push performance to the limit. The model learns from its own outputs, which creates a tighter feedback loop. But for many practical applications, DPO's simplicity and stability make it the right choice.
