Bits and Bytes

I always wonder why in python, sometimes we saw values like 1.000000000000012. Turns out this is determined by the way a floating number is stored in bits. Unlike an integer, which a computer can always store perfectly. It is often the case that a floating number can never be stored perfectly. To store a floating number using 32 (or other number, e.g. 16 or 8) bits, the bits are splited into three different fields: sign, range, and precision. The precision part is unfortunately often truncated, resulting imperfect store for a floating number.

Problem

The slight overflow for us in daily work or life is probably fine (I heard that in bank they store number in integer to avoid this). But consider how it could be problematic in a LLM... with all the layers and computations, the overflow might accumulate. This is also the reason why, even if we set the temperature to 0 in an LLM, the result night still be stochastic, because (1.01 + 2.03) + 3.03 might not be equal to 1.01 + (2.03 + 3.03) for a computer. The order of computation is determined by which GPU finishes the computation first.

Float32 vs Float16

First, what does 32 and 16 means? float32 stores a value using 32 bits (binary digits). float16 stores a value using only 16 bits. Fewer bits means less memory and faster computation, but reduced range and precision.

The Three Components of a Floating-Point Number

A 32-bit float is (typically) divided into three fields like below:

  • Sign (1 bit): 0 = positive, 1 = negative
  • Range (8 bits): Determines the largest (and smallest) numbers the float can represent, it should be 2^(2^8 - 1) = 2^(255) as we will see later.
  • Precision (23 bits): Determines how accurate or fine-grained the representation is

Different formats like TF32 or BF32 allocate different numbers of bits to range and precision, but the total always adds up to their stated bit, in this case 32.

Example: Storing 1234.5678 in Float32

To understand how a floating number is stored, maybe it's best to consider an concrete example.

Step 1: Determine the Sign

1234.5678 is positive, so the sign bit is 0.

Step 2: Convert the Integer Part to Binary

Convert 1234 to binary by repeated division by 2:

1234 in binary = 10011010010

Step 3: Convert the Fractional Part to Binary

Convert 0.5678 to binary by repeated multiplication by 2. At each step, the integer part of the result becomes the next binary digit:

0.5678 x 2 = 1.1356   -> 1
0.1356 x 2 = 0.2712   -> 0
0.2712 x 2 = 0.5424   -> 0
0.5424 x 2 = 1.0848   -> 1
0.0848 x 2 = 0.1696   -> 0
0.1696 x 2 = 0.3392   -> 0
0.3392 x 2 = 0.6784   -> 0
...                    (continues forever)

So the fractional part in binary is approximately 1001000... (it can goes on forever for many decimal fractions...)

Step 4: Combine and Normalize

Putting integer and fractional parts together:

1234.5678  ->  10011010010.10010001...

Now we normalize this into scientific notation (binary), shifting the decimal point left until there is exactly one 1 before it:

10011010010.10010001...
= 1.001101001010010001... x 2^10

We moved the point 10 positions to the left, so the range is 10.

Step 5: Fill in the Fields

  • Sign: 0
  • Range: 10 + 127 = 137, stored as 10001001 (137 in binary)
  • Precision: The digits after the leading 1 (which is implicit and not stored): 00110100101001000101... truncated or rounded to 23 bits

Note the first 1 is not stored, because it is here for any value. This saves us one bit for free.

Why Add 127 to the Exponent? (The Bias)

It is somehow confusing that in the above example, the range part saves 10 + 127, rather than saving 10 directly. This is another clever trick for saving one bit.

Consider a very small number like 0.000010023. In normalized binary scientific notation, the range could be negative (e.g., 2^(-5) or smaller). Without a bias, we would need a separate sign bit for the range.

Instead, we add 127 to the actual exponent before storing it：

  • An actual exponent of -1 is stored as -1 + 127 = 126
  • An actual exponent of +10 is stored as 10 + 127 = 137
  • So, the stored value is always positive between 0 and 255.

The bias trick eliminates the need for a separate sign bit on the range, saving one bit and simplifying hardware comparison of floating-point numbers.

Summary

  • Floating-point numbers are stored as: (-1)^sign x 1.pricision x 2^(range - 127)
  • More range bits = larger range; more precision bits = finer precision, always a trade-off (like everything else)
  • The range bias term (127) allows negative range without a sign bit (127 for float32, 15 for float16)
  • Most decimal fractions cannot be represented exactly in binary, hence rounding errors
