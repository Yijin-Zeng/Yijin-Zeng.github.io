Sparse Retrieval

Machine Learning

A concise handwritten version of this note is available as a PDF.

Sparse retrieval represents data using sparse vectors. It has two main branches: exact keyword matching (e.g. TF-IDF, BM25), and sparse semantic embedding (e.g. SPLADE).

TF-IDF (Term-Frequency Inverse-Document-Frequency)

TF is the count of a word wi in a document Dj, written as f(wi, Dj). The intuition is that if a word appears frequently in a document, this document is more likely to be about this word.

IDF is defined as:

IDF(wi) = log(N / DF)

where N is the total number of documents, and DF is the number of documents containing this word. Note that IDF is a function of wi only. The intuition here is that if a word appears in all (or most) documents, it is probably not very important, e.g. "the", "a", "an".

Given a query, how TF-IDF retrievaling relevant documents:

  1. Let w1, w2, ..., wq be the words in the query.
  2. Compute f(wi, Dj) for all i = 1, ..., q, j = 1, ..., N.
  3. Compute IDF(wi) for all i = 1, ..., q.
  4. For a given document Dj, the score of TF-IDF for this query is:
score(Dj) = Σi=1,...,q f(wi, Dj) · IDF(wi)

A few notes about TF-IDF. First, in TF-IDF the term frequency in the query itself is not used (it is always set to 1). Second, the score of TF-IDF scales linearly with the word frequency in the document, this means if word i appears 10 times more, the score for this word is 10 times larger. This biases the retrieval results towards long documents. Also, if a word already appears many times, the importance of this word should somehow be saturated rather than growing infinitely.

BM25 (Best Matching 25)

BM25 improves on TF-IDF for addressing bias towards long documents and the linear increase with word frequency. For a given document Dj, the BM25 score for the query (with b normally between 1-2) is calculated as:

score(Dj) = Σi=1,...,q IDF(wi) · [ f(wi,Dj)(k1+1) ] / [ f(wi,Dj) + k1(1 - b + b · dj/avgk(dk)) ]

where dj is the document length of Dj, and avgk(dk) is the average document length. This can be rewritten as:

score(Dj) = Σi=1,...,q IDF(wi) · (k1+1) / [ 1 + k1(1 - b + b · dj/avgk(dk)) / f(wi,Dj) ]

The (1 - b + b · dj/avg) term penalizes Dj if dj is large. Also, the effect of f(wi,Dj) saturates fast, the whole fraction approaches a constant as f grows, instead of scaling linearly like TF-IDF did.

SPLADE (Sparse Lexical AND Expansion)

TF-IDF and BM25 are both based on exact word matching. They are very effective and can be very strong baseline for any other retrieval methods to beat. However, they both ignores the semantic meaning completely. For example, if the query is: "Can you recommend me a cheap laptop?" but a document using keyword such as affordable computer, then this document will be ignored by exact word matching methods.

SPLADE is a combination of sparse and dense retrieval. It produces embedding for a query or a document the length of all possible words, where only the semantic relevant words for the query or the document will be assgined positive weights. Hence, the embedding is sparse encodes semantic meaning.

To understand how SPLADE encodes a query (or document), let's consider an example query, "Can you recommend me a cheap laptop?" This is passed through a fine-tuned BERT (or other encoder) to get a contextual embedding for each word (paying attention to the whole sequence, including itself). This embedding is then passed to the final layer of the fine-tuned BERT model to get logits for all words, e.g. if we take the embedding for the word "cheap" we may get logits for each word looks like this: cheap 7.3, affordable 5.4, reasonable 2.1, ... (most words are 0.0).

Let us denote the embedding for this query as w, where w_j is the weight for word j accross all possible words. If Lij is the logit for word j at query position i, the final weight wj is:

wj = maxi [ log(1 + ReLU(Lij)) ]

taking the max over all positions i in the query. This filters out small logits , so the embedding vector w for the query ends up very sparse. We do the same for each document to get a sparse embedding for each document as well. Retrieval is then just the dot product between the embeddings of the query and the documents. \ This is quick because the embeddings are sparse.

How Is BERT Fine-Tuned for SPLADE?

The loss function for fine-tunining BERT is: 
L = Lcontrastive + λq · Lflops(q) + λd · Lflops(d),
where the embeddings for document or query are calculated as we described above.

The FLOPS term encourages sparsity for the query/document embedding:

Lflops = Σj (w̄j)²,   where w̄j = (B/|batch|) Σ |wj|

This is to encourage sparsity regularization for the embedding. Because it is computed across the batch, if a word is non-zero for one sequence in the batch, the penalty on that word's loss ends up penalizing the outcome for many sequences in the batch.

For the contrastive part, with batch size B and pairs q1↔d1, q2↔d2, ..., qB↔dB:

Lcontrastive = -Σi log( esim(qi,di) / Σj esim(qi,dj) )

where sim(·,·) is the dot product (or cosine similarity) of the embeddings of qi and dj. Unlike CLIP, this loss is not symmetric， the sum in the denominator scales across documents only, because we only care about given one query, which document matches the most. In CLIP, we care about both directions.

Summary

  • Sparse retrieval represents data with sparse vectors, either through exact keyword matching (TF-IDF, BM25) or sparse embedding (SPLADE).
  • TF-IDF scores a document by summing f(wi,Dj) · IDF(wi) over query words, but it scales linearly with term frequency and is biased towards long documents.
  • BM25 fixes this by adding a saturating term (via k1) and document-length normalization (via b).
  • SPLADE gets a sparse-but-semantic embedding by turning masked-LM-style contextual logits into a sparse weight vector via max-over-query-positions of log(1+ReLU(logit)), then retrieves via a fast sparse dot product.
  • SPLADE is trained with a FLOPS sparsity regularizer on both query and document embeddings, plus an asymmetric contrastive loss.
