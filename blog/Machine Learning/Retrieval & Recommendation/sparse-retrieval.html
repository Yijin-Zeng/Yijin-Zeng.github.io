Sparse Retrieval

Machine Learning

A concise handwritten version of this note is available as a PDF.

Sparse retrieval represents data using sparse vectors. It has two branches: exact keyword matching (e.g. TF-IDF, BM25), and sparse embedding (e.g. SPLADE).

TF-IDF (Term-Frequency Inverse-Document-Frequency)

TF is the count of a word wi in a document Dj, written f(wi, Dj). The intuition: if a word appears frequently in a document, this document is more likely to be about this word.

IDF is defined as:

IDF(wi) = log(N / DF)

where N is the total number of documents, and DF is the number of documents containing this word. Note that IDF is a function of wi only. The intuition: if a word appears in all (or most) documents, it is probably not very important, e.g. "the", "a", "an".

How TF-IDF works:

  1. Let w1, w2, ..., wq be the words in the query.
  2. Compute f(wi, Dj) for all i = 1, ..., q, j = 1, ..., N.
  3. Compute IDF(wi) for all i = 1, ..., q.
  4. For a given document Dj, the score of TF-IDF for this query is:
score(Dj) = Σi=1q f(wi, Dj) · IDF(wi)

A couple of things to note. First, in TF-IDF the term frequency in the query itself is not used (it is always set to 1). Second, the score of TF-IDF scales linearly with the word frequency in the document — if word i appears 10 times more, the score for this word is 10 times larger. This biases the retrieval results towards long documents. Also, if a word already appears many times, the importance of this word should somehow be saturated rather than growing infinitely.

BM25 (Best Matching 25)

BM25 improves on TF-IDF. For a given document Dj, the BM25 score for the query (with b normally between 1-2) is:

score(Dj) = Σi=1q IDF(wi) · [ f(wi,Dj)(k1+1) ] / [ f(wi,Dj) + k1(1 - b + b · dj/avgk(dk)) ]

where dj is the document length of Dj, and avgk(dk) is the average document length. This can be rewritten as:

score(Dj) = Σi=1q IDF(wi) · (k1+1) / [ 1 + k1(1 - b + b · dj/avgk(dk)) / f(wi,Dj) ]

The (1 - b + b · dj/avg) term penalizes Dj if dj is large. This "saturates" f(wi,Dj) — the whole fraction approaches a constant as f grows, instead of scaling linearly like TF-IDF did.

SPLADE (Sparse Lexical AND Expansion)

SPLADE is a combination of sparse and dense retrieval. Why? Because the vector it produces is sparse but encodes semantic meaning.

How SPLADE encodes a query (or document): take an example query, "Can you recommend me a cheap laptop? I will mainly use for video games." This is passed through a fine-tuned BERT (or other encoder) to get a contextual embedding for each word (paying attention to the whole sequence, including itself). This embedding is then used to get logits for all words — e.g. if we mask the word "cheap" we may get logits: cheap 7.3, affordable 5.4, reasonable 2.1, ... (most words are 0.0).

If Lij is the logit for word j at query position i, the final weight wj is:

wj = maxi [ log(1 + ReLU(Lij)) ]

taking the max over positions i in the query. This filters out "extreme" logits (those that are small), so the embedding vector w for the query ends up very sparse. We do the same for each document to get a sparse embedding for each document as well. Retrieval is then just the dot product between the embeddings of the query and the documents — this is quick because the embeddings are sparse.

How Is BERT Fine-Tuned for SPLADE?

L = Lcontrastive + λq · Lflops(q) + λd · Lflops(d)

The FLOPS term encourages sparsity for the query/document embedding:

Lflops = Σj (w̄j)²,   where w̄j = (B/|batch|) Σ |wj|

This is spoken of as "sparsity regularization" for the embedding. Because it is computed across the batch, if a word is non-zero for one sequence in the batch, the penalty on that word's loss ends up penalizing the outcome for many sequences in the batch.

For the contrastive part, with batch size B and pairs q1↔d1, q2↔d2, ..., qB↔dB:

Lcontrastive = -Σi log( esim(qi,di) / Σj esim(qi,dj) )

where sim(·,·) is the dot product (or cosine similarity) of the embeddings of qi and dj. Unlike CLIP, this loss is not symmetric — the sum in the denominator scales across documents only, because we care only about, given one query, which document matches the most. In CLIP, we care about both directions.

Summary

  • Sparse retrieval represents data with sparse vectors, either through exact keyword matching (TF-IDF, BM25) or sparse embedding (SPLADE).
  • TF-IDF scores a document by summing f(wi,Dj) · IDF(wi) over query words, but it scales linearly with term frequency and is biased towards long documents.
  • BM25 fixes this by adding a saturating term (via k1) and document-length normalization (via b).
  • SPLADE gets a sparse-but-semantic embedding by turning masked-LM-style contextual logits into a sparse weight vector via max-over-query-positions of log(1+ReLU(logit)), then retrieves via a fast sparse dot product.
  • SPLADE is trained with a FLOPS sparsity regularizer on both query and document embeddings, plus a contrastive loss that — unlike CLIP's — is asymmetric, since retrieval only cares about which document best matches a given query.
