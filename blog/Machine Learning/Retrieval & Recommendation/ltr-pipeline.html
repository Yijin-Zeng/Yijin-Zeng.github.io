LTR Pipeline

Machine Learning

A concise handwritten version of this note is available as a PDF.

Here we consider how a learning to rank (LTR) pipeline works end to end, from data collection to inference. This builds on the pointwise, pairwise, and listwise losses covered in Learning to Rank Algorithms.

Data Part

Data collection for learning to rank splits into explicit feedback and implicit feedback.

Explicit feedback: query q_i gives documents D_i,1, ..., D_i,K_i, a human sorts the results, and we get scores (e.g. ranks) S_i,1, ..., S_i,K_i.

Pros: the dataset is clean and unbiased.
Cons: too expensive, and cannot scale easily.

Implicit feedback relies on actual user data for labeling. We focus on implicit feedback here because it is more practical. We log different users' behavior, such as:

  1. Impression: which item was physically shown to the user. E.g. if the user didn't scroll down to item 7, then it should not be logged as an impression.
  2. Click: which item is clicked.
  3. Dwell time: how long a user stays on an item.
  4. Conversions: if a user paid for an item.

And more. Using the logged info, we can start training models for prediction (e.g. click-through rate, conversion rate, etc.).

Pointwise Approach

Click-through rate (CTR) model: we can train a model to predict CTR using the items given an impression:

context info, user info, product info, display position info, match score  →  model  →  P(click | impression)

Similarly, we can train a conversion rate model using the items clicked: P(conversion | click). Then we can compute the score for an item as:

Expected revenue = P(click | impression) · P(conversion | click) · revenue

where revenue comes from the business side, since we care about revenue.

Pros: get well calibrated probabilities (not perfectly, though).
Cons: it ignores the rank (score) between recommended documents completely. Two predictions can have the same relative ordering error, but very different loss, depending only on how confident (or wrong) each individual probability is -- the loss doesn't care whether the ordering between documents comes out correct.

Listwise or Pairwise Approach

To train listwise or pairwise models, we need to score each item, e.g.:

purchase   → score 4
add to cart → score 3
click       → score 2
dwell       → score 1

Then we can scale the score by the location of each item. E.g. if both item 1 and item 2 are clicked, but item 1 is ranked on top, we give item 2 a higher score -- getting a click while ranked lower is a stronger signal than getting a click while ranked on top.

Pros: it learns from our target (good rank) directly.
Cons: the probability is not calibrated; harder to train.

Combining Pointwise and Listwise/Pairwise Loss

The probability from the model can be used for both the pointwise loss and the listwise/pairwise loss at once. This way we get better probabilities: well calibrated, and taking the score into account.

Offline Metrics for Evaluating Ranking Quality

Normalized Discounted Cumulative Gain (NDCG):

DCG_i = Σ_{j=1}^{k_i} S_i,j / log₂(j+1)

where S_i,j is the score of the document for query i at position j (given by the model), and the label comes from, e.g., purchase → 4, add to cart → 3, click → 2, dwell → 1.

iDCG_i = DCG_i if the model ranks perfectly (top → bottom = highest score → lowest score)

NDCG_i = DCG_i / iDCG_i

iDCG_i is the ideal DCG -- the best possible DCG for that query, used to normalize DCG_i so scores are comparable across queries with different numbers of documents.
