Dense Retrieval

Machine Learning

A concise handwritten version of this note is available as a PDF.

Dense retrieval uses dense vectors for retrieval, i.e. semantic retrieval. There are three main approaches: bi-encoders (fast but relatively low retrieval quality), cross-encoders (slow but very high retrieval quality), and late-interaction models (in the middle for both speed and quality).

Bi-Encoders

In a bi-encoder, the query and each document are encoded completely separately:

Query      --> encoder --> embedding
Document   --> encoder --> embedding

Normally the same encoder (the same model, tied weights) is used for both the query and the documents. During retrieval, we can use Approximate Nearest Neighbors (ANN) methods such as HNSW to find the top-k documents efficiently.

Example: Sentence-BERT

Sentence-BERT fine-tunes BERT for embedding sentences. To use it for comparing the similarity of two paragraphs， sentence-BERT do the following steps: 

Sentence A --> BERT --> mean pooling --> vector u
Sentence B --> BERT (same model, tied weights) --> mean pooling --> vector v
u, v --> cosine similarity

How is it fine-tuned? It is noramlly fine-tuned on Natural Language Inference (NLI) task for understanding the meaning of sentences. In NLI, we prepare an input as tokens of A + special sep token + tokens of B + special sep token. Then we let the model decide if A and B has the following relationships:

  1. Entailment of A: A => B, if A is true, B is true.
  2. Contradiction of A: A ≠> B, if A is true, B is false.
  3. Neutral: A -/-> B or A -/-> ¬B.
We can see that for the NLI task, the order of the two sentences is crucial, so Sentence-BERT builds a longer feature vector containing u, v, and |u-v|, and uses this to classify the relationships.

Why is |u-v| in there? If A and B are very similar, BERT produces similar u and v, so the model learns that when |u-v| is small, the pair is likely entailment. In other words, BERT and the final classification network learn to exploit the fact that a small |u-v| signals entailment, and so they learn to push u ≈ v when entailment is true.

Pros of bi-encoder: fast and efficient: all documents are embedded and stored as vectors ahead of time, ready for retrieval.
Cons of bi-encoder: the embedding quality is relatively low. Embeddings for queries and documents are embedded independently. During embedding, the document does not know what the queries would be and query does not know what document would be. So the embeddings can only represent general semantic meaning of documents or queries.

Cross-Encoders

Cross-encoders are also called early interaction models. The input is:

<CLS> + Query + <SEP> + Document + </SEP>
--> fine-tuned BERT
--> relevance score, using the contextual embedding of <CLS>

Score = wT · <CLS>

How is BERT fine-tuned for a cross-encoder? There are normally two common ways:

  1. (Pointwise loss) BERT + a sigmoid adapter at the end, trained as a classification task (1 if the query matches the document, 0 if not).
  2. (Pairwise loss) BERT + a sigmoid adapter at the end, trained with a pairwise loss: -log(sigmoid(sig(q,d+) - sig(q,d-))), where d+ is the matched document and d- is the unmatched document.

Why is a cross-encoder much more powerful than a bi-encoder? In a bi-encoder, the query and the document are embedded completely independently. At best, a document's embedding only captures what the document is generally about, the best it can do is "be average" over all the queries it might be relevant to, because it never sees the query while being embedded, so it has to work reasonably well for all related queries. A cross-encoder, by contrast, learns the relevance between the document and the specific query.

Cons of cross-encoder: it is very slow, we need to embed the query together with every document, for every single retrieval.

Late-Interaction (ColBERT)

ColBERT stands for contextualized late interaction over BERT. In a bi-encoder, we use one single embedding vector for the whole query and the whole document. In ColBERT, the embedding for each token is kept instead.

So a document i with 500 words becomes an embedding matrix Ei ∈ R 500×d (e.g. d = 1024). A query j with 10 words becomes Eqj ∈ R10×d. The relevance score is:

S(q_j, d_i) = Σ_{tokens in query} max_{tokens in document} ( E_qj · E_diT, dim=-1 )

In other words, the similarity between the query and a document is computed as follows: for each token in the query, compute its similarity against every token in the document and take the maximum (the most similar document token); then sum these maximum similarities across all tokens in the query.

Pros: this is better than a bi-encoder because it captures token-level detail instead of collapsing everything into one sentence-level vector.
Cons: it takes a huge amount of storage room, since every token of every document needs its own embedding.

Summary

  • Dense retrieval uses dense vectors for semantic retrieval, with three main approaches trading off speed against quality.
  • Bi-encoders embed the query and documents independently, enabling fast ANN search (e.g. HNSW), but embeddings can only be "average" over related queries, so quality is lower.
  • Sentence-BERT fine-tunes bi-encoders using NLI, building a feature vector of u, v, and |u-v| so the model can learn that small |u-v| signals entailment.
  • Cross-encoders jointly encode the query and document together, learning relevance specific to that pair, which makes them much more powerful — but very slow, since every document must be re-encoded with the query at retrieval time.
  • Late-interaction models (ColBERT) keep per-token embeddings and score with a sum-of-max operation, landing in the middle: better quality than bi-encoders via token-level detail, but with much larger storage cost.
