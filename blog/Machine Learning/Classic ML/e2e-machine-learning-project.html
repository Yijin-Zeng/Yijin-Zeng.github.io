E2E Machine Learning Project Checklist

Machine Learning

A concise handwritten version of this note is available as a PDF.

I wrote this note after about a year working as an ML scientist, as a reflection and also a checklist for myself: whenever I'm assigned a new ML project, what should I actually be thinking about?

Step 1: Look at the Big Picture

  • What is the task? At the beginning, ask what the input and the output are, and then decide what kind of problem it is: classification, regression, or outlier detection. Understand the scale of the data and the model. These are all important for framing the problem at hand. Sometimes it is possible to frame the same problem in different ways. For example, detecting spam email can be considered either a classification problem or an outlier detection problem. How we frame the problem is crucial in many cases: it decides the difficulty, and whether the problem can be solved successfully at all.
  • How will the model be used? Machine learning model rarely lives in a vaccume. It's normally only one part of a bigger picture. It could be used to make predictions directly in a production pipeline, to extract internal knowledge, or its outputs could feed into another downstream model. How the model will be used is a big factor in deciding the approach for the task. For example, if we are training an embedding model to be used by other downstream classification models, the quality of the embedding matters more than the output accuracy of the embedding model itself.
  • Any constraints? Ask if there are any hard constraints (must have), any soft constraints (better to have), and also think about whether these constraints could change. There will often be latency requirements, business requirements (e.g. if we are pricing a product, the business partner may want a margin of 10-15% for the product), and these constraints could change frequently. If this is the case, it is worth designing the pipeline so that constraint can be processed modularly, rather than retraining an end-to-end model every time it changes.
  • How would we evaluate the success of the project? It's useful to think at the beginning about how to measure the success of the project, because there could be many factors to decide this. For example, would a classification model with similar accuracy but less latency be a win? If the new model has smaller loss compared to the older model in general, but performs worse for more important business partners, should we decide this is a win or a loss? Normally, it's better to have a decisive metric, but it's also important to have a set of guardrail metrics to make sure things are not going very wrong along some other dimension. It is also very important to have a baseline model to compare against, either a naive solution or an older model.
  • Timeline and compute. If the project is 1 month vs 1 year, the solution is probably very different, depending on how much resource we have. Plan the project beforehand: there will always be more things to do with the data and the model, but we must stop at some point. For this reason, it's always better to get each part (data, model, evaluation) to a basic level first, rather than digging too deep into the model, only to realize at the end of the project that the data has serious issues.

Step 2: Get the Data

Surprisingly, this step is actually non-trivial in many cases. Say we want to predict how likely a customer will buy a book. We probably need to fetch from several tables: customer metadata (age, gender, ...), customer purchase history, book info (year, genre, publisher, ...), and maybe publisher info too.

  • Because data are usually stored in different places, it is usually non-trivial to get all the data and join them into the form we want. (many errors could happen at the join step for various reasons, so need to be extra carefully)
  • Sometimes we also only use a specific scope of data, e.g. one model for customers in the US, one for Europe (there may be laws that prevent using certain features for customers in a given region), so we need to apply correct filter. It is possible, however, a complex business logic needs to be applied to get the correct scope.
  • More often than not, table have different versions and dependencies. We need to understand which version we need to use for each table. For example, if we decide to use version 3 for table A, then we might need to use version 4 for table B.
  • There could be different data sources for the data we want to use, e.g. one from analytics team one from engineering team. 99% of their data are the same, but it is not always easy to understand why that 1% of data are different, or what impact it might have to models.

Step 3: Get Insights From the Data

It's better to spend more time on the data than the model. It saves a lot of headaches later. If a model doesn't work as expected, the answer is very likely in the data.

Things to consider (standard for almost all ML projects):

  • Duplication, missing data, outliers, data distributions, feature correlations
  • Whether the train and validation data come from the same distribution
  • For classification, whether the labels are balanced

There is much more to consider in a real project, case by case. For example:

  • Is the data source reliable? Can we trust the data? E.g. if we have browsing data, is it generated by humans or by malicious bots? It's also normal that some business logic is needed to derive certain features, e.g. price = f(location, month, product). Check if the logic is implemented correctly.
  • Is there any business changes behind the data? A business configuration change at a certain point in time can have a big impact on the data.

The reason it is better to spend more time on the data: issues related to the data are normally very hidden, unless we have good insight into the data.

First real example: training data from 2025-01-01 to 2025-12-31 gave a good model, but validation data from 2026-01-01 to 2026-03-31 made the model perform much worse. The reason turned out to be a big configuration change for one very big partner in 2026.
Second real example: during a project to include service fee into the training and inference pipeline, some partners see much bigger change because of service fee than the others. The reason turned out to be that the service fee is in local currency (e.g. Yen or British Pounds), but the profit is always in USD.

Step 4: Pre-process the Data for Training

  • This step is in general more standard after we have a good insight into the data: impute missing data, remove outliers, scale the data, feature selection and feature engineering.
  • If the input is sequential (e.g. RNN or Transformer), use a sliding window.
  • One thing worth to consider in this step is how sensitive is the model to preprocessing choices? E.g. mean imputation vs. hot-deck imputation, or an RNN being sensitive to the window size.

Step 5: Model Training

In many cases, this is usually the easy part of a ML project.

  • Start from a simple model e.g. linear regression and logistic regression, or for time series, using the last data point as the prediction, etc. This gives us two things: a baseline for any more complex model, and additional insight about the data and the problem.
  • Plan experiments carefully. Don't think we can push all experiments at once. This process could be iterative with our understanding of the data, model and the project. Different hyperparameters take time and compute, if constrained, think about what is a must-run and what can be sacrificed (e.g. some experiments run on a smaller dataset to save time and compute). Instead of pushing all experiments at once, always start from simpler, smaller experiments first, to make sure things work as expected.
  • After model training, there may be some post-processing needed to satisfy constraints (e.g. one partner may ask all products to have an average margin of 10%).
  • There will also sometimes be approaches to improve performance further, e.g. ensembling, or if a certain type of data isn't working well with the main model, maybe training a separate model for it, or routing it to a simpler model instead. Again, this process also helps us understand the data and the model better.

Step 6: Model Evaluation

Model evaluation is a crucial step that allows us to understand a model's behavior, estimate its real-world performance, and assess its potential business impact before it is launched.

While training and validation metrics (e.g., MSE, cross-entropy loss) provide a high-level overview of how a model is learning, a single score rarely captures the full context we care about in a machine learning project. Relying solely on one overarching metric can sometimes also be misleading (e.g., due to Simpson's paradox). Comprehensive model evaluation depends heavily on the specific goals of the project and requires insights from human domain experts.

Some aspects to consider during model evaluation include:

  • Performance across data slices: How does the model perform across different subgroups? It is often very important to break down metrics by time periods, user demographics, geographic locations, or customer segments to ensure consistent performance across the board.
  • Baseline and heuristic comparisons: Is the model actually adding value? We must compare the model's performance against simple baselines (e.g., always predicting the historical average), existing rule-based heuristics, or the legacy model currently running in production.
  • Alignment with business metrics: Statistical metrics like AUC or F1-score do not directly translate to business value. We need to estimate how the model's predictions will impact core business objectives, such as conversion rates, user retention, or revenue generation.
  • Robustness and stability: How does the model react to unexpected inputs or changing environments? Evaluation should test how the model handles noisy data, missing features, or long-term shifts in data distribution (data drift).
  • Failure modes and edge cases: Under what specific conditions does the model completely break down. Understanding exactly when and why a model fails, such as encountering outliers or unusual scenarios can help establish safety guardrails to prevent catastrophic results. This is especially critical in certain domains like autonomous driving or healthcare.
  • Fairness and bias: Does the model systematically disadvantage certain groups? This is especially important when concerning some attributes like race, gender, or age, to ensure ethical and equitable outcomes.
  • System performance and latency: A highly accurate model is useless if it is too slow or expensive to run. Evaluation must include operational metrics like inference latency (response time), memory footprint, and computational cost at scale.
  • Interpretability: Can we explain why the model made a specific prediction? Using techniques like SHAP or LIME to extract feature importance helps build trust with stakeholders and allows experts to verify that the model is learning logical relationships.
  • Identify potential improvement paths: Evaluation also helps us to identify the potential rooms for improving the model. For example, if a classfication model often confuse between class A and B, then it might be helpful to feed more examples of the two classes. By identifying which hyperparameters have the most significant impact on performance (e.g., using sensitivity analysis to map hyperparameters to validation loss), we can efficiently allocate our time and compute budget for tuning them.

Steps 3, 4, 5, and 6 are iterative. In the end, we get better at understanding the data, the model, and the task together.

Step 7: Model Deploy, Monitor, and Maintain

Getting a model ready for deployment is a big part of the project, but often not the whole part. We also need to think how to deploy the model in production enviroment and how to maintain it.

  • Deployment: Deploying a model can range from a simple script to a highly complex system, depending largely on the project itself and existing infrastructure and workflow. Normally, transitioning a model from an experimental notebook to a production environment requires consider the following components:
    • Orchestration: If model development happened mainly in a single notebook, then we need to consider how to factor the monolithic code into a modular pipeline. Orchestration tools (like airflow and flyte) manage the complex sequence of independent steps, such as data extraction, preprocessing, inference, and writing results back to a database. We need to ensure data flows correctly from one step to the next and handling potential fails.
    • Scheduling: In a notebook, we manually executes the code cells. In production, the model needs an automated trigger. A scheduler dictates when the pipeline runs. This could be on a fixed time interval (e.g., a nightly batch job), triggered by an event (e.g., new data arriving in a data lake).
    • Environment Reproducibility: Notebooks often rely on hidden local configurations or manually installed packages that aren't documented. To deploy safely, we must specify the exact software environment—including Python versions and specific library dependencies. Consider using tools like Docker containers to run the model runs identically in the production server as it did on cloud or local machine.
    • Infrastructure & Compute: A model running on a laptop or a cloud notebook cannot support production traffic or massive datasets. We must determine the physical or cloud infrastructure required to serve the model (such as Kubernetes clusters, serverless functions, or dedicated GPU instances), ensuring the system has the memory and CPU power to scale with user demand.
  • Monitor and maintain: In real world production environments, data is almost never I.I.D. (Independent and Identically Distributed). In practice, the data distributions during training and evaluation frequently differ from what the model processes in production. This distribution shift can sometimes be abrupt, such as a sudden market shock in finance or a rapid viral trend on TikTok. However, in most cases, the shift is gradual (often referred to as data drift), causing the model's predictive quality to degrade slowly over time. Therefore, it is critical to continuously monitor model performance in production and establish automated triggers to retrain the model whenever performance drops below an acceptable threshold.
