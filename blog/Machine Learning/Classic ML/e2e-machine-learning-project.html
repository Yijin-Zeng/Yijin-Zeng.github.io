What to Consider When Assigned a Machine Learning Project

Machine Learning

A concise handwritten version of this note is available as a PDF.

I wrote this note after about a year working as a machine learning scientist, as a checklist for myself: whenever I'm assigned a new ML project, what should I actually be thinking about? The steps below go from framing the problem to keeping the model alive in production.

Step 1: Look at the Big Picture

What is the task? Input to output, and whether it's classification, regression, or outlier detection. Sometimes it is possible to frame the same problem in different ways -- e.g. detecting spam email can be considered either a classification problem or an outlier detection problem. How we frame the problem is crucial in many cases: it decides the difficulty, and whether the problem can be solved successfully at all.

How will the model be used? It could be used directly in a production pipeline, or it could feed another model. For example, if we are training an embedding model to be used by another classification model downstream, the quality of the embedding matters more than the output accuracy of the embedding model itself.

Any constraints? Latency requirements, business requirements (e.g. if we are pricing a product, the business partner may want a margin of 10-15%), and these constraints could change frequently. If the requirements for a constraint change often, it is worth designing the pipeline so that constraint can be processed modularly, rather than retraining an end-to-end model every time it changes.

How would we evaluate the success of the project? It is important to have a baseline model to compare against, either a naive solution or an older model. The actual metric -- A/B test accuracy, latency, simplicity -- depends a lot on how the model will be used.

Timeline and compute. If the project is 1 month vs. 1 year, the solution is probably very different, depending on how much resource we have. Plan the project beforehand: there will always be more things to do with the data and the model, but we must stop at some point.

Step 2: Get the Data

This step is actually non-trivial in many cases. Say we want to predict how likely a customer will buy a book. We probably need to fetch from several tables: customer metadata (age, gender, ...), customer purchase history, book info (year, genre, publisher, ...), and maybe publisher info too.

Because data are usually stored in different places, it is usually non-trivial to get all the data and join them into the form we want. Sometimes we also use a specific scope of data -- e.g. one model for customers in the US, one for Europe -- and there may be laws that prevent using certain features for customers in a given region.

To make things worse, each table may have different versions. In the worst case, always check that the column names still match.

Step 3: Get the Insights From the Data

Spend more time on the data than the model, because it saves a lot of headaches later. If a model doesn't work as expected, the answer is very likely in the data.

Things to consider (standard for almost all ML projects): duplication, missing data, outliers, data distributions, feature correlations, whether the train and validation data come from the same distribution, and -- for classification -- whether the labels are balanced.

There is more to consider in a real project:

  • Is the data source reliable? Can we trust the data? E.g. if we have browsing data, is it generated by humans or by malicious bots? It's also normal that some business logic is needed to derive certain features, e.g. price = f(location, month, product) -- is that logic actually correct?
  • Is the data IID? A business configuration change at a certain point in time can have a big impact on the data.

The reason it is better to spend more time on the data: issues related to the data are normally very hidden, unless we have good insight into the data. A real example: training data from 2025-01-01 to 2025-12-31 gave a good model, but validation data from 2026-01-01 to 2026-03-31 made the model perform much worse. The reason turned out to be a big configuration change for one very big partner in 2026.

Step 4: Pre-process the Data for Training

This is more standard: impute missing data, remove outliers, scale the data. If the input is sequential (e.g. RNN or Transformer), use a sliding window. Also feature selection and feature engineering.

One thing to consider: how sensitive is the model to preprocessing choices? E.g. mean imputation vs. hot-deck imputation, or an RNN being sensitive to the window size.

Step 5: Model Training

The most enjoyable part, and surprisingly, the easy part.

Start from a simple model -- e.g. linear regression and logistic regression, or for time series, using the last data point as the prediction, etc. This gives us two things: a baseline for any more complex model, and additional insight about the data and the problem.

Plan experiments carefully. Different hyperparameters take time and compute -- if constrained, think about what is a must-run and what can be sacrificed (e.g. some experiments run on a smaller dataset to save time and compute). Instead of pushing all experiments at once, always start from simpler, smaller experiments first, to make sure things work as expected.

After model training, there may be some post-processing needed to satisfy constraints (e.g. one partner may ask all products to have an average margin of 10%). There will also sometimes be approaches to improve performance further, e.g. ensembling, or if a certain type of data isn't working well with the main model, maybe routing it to a simpler model instead.

Step 6: Model Evaluation

It can be easy: just look at the loss function for all models and pick the best one. For classification, check which class performs the best; for regression, consider analyzing why some data points have a worse prediction.

It can also be comprehensive: how does performance change over time, by partner, or by location? Among all hyperparameters, which one has the biggest impact on model performance (e.g. run a random forest using hyperparameters as inputs and losses as targets), so we can spend more time and compute fine-tuning that parameter. And how do we connect the offline result to online performance?

Steps 3, 4, 5, and 6 are iterative. In the end, we get better at understanding the data, the model, and the task together.

Step 7: Model Deploy, Monitor, and Maintain

Deploy: check the environment, and for different parts of the pipeline, choose reasonable compute resources. Consider how much traffic we'll get if A/B testing is needed.

Monitor: data quality checks, automatic model performance monitoring, and when to scale the traffic up or down.

Maintain: prepare to update parts of the pipeline, and be ready to update the whole pipeline. If something unexpected happens, consider how to fall back safely.

Summary

  • How a problem is framed (step 1) can decide whether it's solvable at all, before any data or model is involved.
  • Getting and understanding the data (steps 2 and 3) is usually where the real difficulty and the real payoff are -- most model problems trace back to a data problem.
  • Model training (step 5) is often the easy and enjoyable part, precisely because steps 1-4 did the hard work already.
  • Steps 3 through 6 are iterative, not a one-way pipeline.
  • The job isn't done at deployment -- monitoring and maintaining the pipeline (step 7) is what keeps a model useful over time.
