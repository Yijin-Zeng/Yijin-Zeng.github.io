From SGD to Adam

Machine Learning

A concise handwritten version of this note is available as a PDF.

Stochastic gradient descent (SGD) updates the parameters using the gradient of the loss, computed over a batch rather than the full dataset -- that's the "stochastic" part:

θ⁽ᵗ⁺¹⁾ ← θ⁽ᵗ⁾ − η ∇L(θ⁽ᵗ⁾)

Adam is not a separate idea from SGD. It's SGD with a small number of fixes stacked on top of each other, and each fix addresses one concrete failure mode. Going through them in order -- momentum, Nesterov's tweak to momentum, then AdaGrad-style per-coordinate scaling -- is the most direct way to see why the final Adam update looks the way it does.

Momentum: Keeping a Running Velocity Instead of Just the Gradient

Momentum introduces a velocity term m, updates it using the gradient, and then moves θ by m instead of by the gradient directly:

m⁽ᵗ⁺¹⁾ ← α m⁽ᵗ⁾ − η ∇L(θ⁽ᵗ⁾)
θ⁽ᵗ⁺¹⁾ ← θ⁽ᵗ⁾ + m⁽ᵗ⁺¹⁾

This has two advantages over plain SGD.

It accelerates when the gradient direction is consistent

Suppose the gradient is a constant g at every step. Unrolling the recursion for m gives a geometric series:

m⁽¹⁾ = −ηg
m⁽²⁾ = −ηg − αηg
m⁽³⁾ = −ηg − αηg − α²ηg
  ⋮
m⁽ⁿ⁾ = −(1 + α + ... + αⁿ⁻¹) ηg  =  −(1 − αⁿ)/(1 − α) · ηg

As n → ∞, m⁽ⁿ⁾ → −ηg / (1 − α). With α = 0.9, that limit is −9ηg, i.e. 10 times the plain gradient step. So momentum accelerates the update whenever the gradient keeps pointing the same way for a stretch of steps.

There's a second benefit that shows up specifically in the stochastic setting. Batch gradients are noisy, and that noise is roughly random from one batch to the next. Averaging the gradient over time (which is what the recursion for m does) means the random component tends to cancel out while the consistent component keeps accumulating:

without momentum:          with momentum:
                                  ↗
        ↗                       ↗
      ↘   ↗                    ↗
        ↗    (random parts    ↗
      ↘        cancel out)   ↗

It can skip a local minimum

Because momentum carries velocity from previous steps, it can coast through a small dip in the loss surface that would trap plain SGD:

\
 \                 momentum can skip it easier
  \             ↗ - - - ↘              /
   \           /         ↘          /
    \_  _  _  /            ↘_ _  _/
      \/  ← SGD gets
            stuck here

Nesterov Accelerated Gradient: Take the Gradient Where Momentum Is About to Land

Nesterov's observation is that the momentum vector, in general, already points roughly towards the minimum. If that's true, why take the gradient at the current, stale point?

Plain momentum goes from point A to B by adding the gradient at A, then from B to C by adding momentum. Nesterov instead applies the momentum step first: it jumps from A to the lookahead point D = θ⁽ᵗ⁾ + αm⁽ᵗ⁾, takes the gradient there, and only then combines that gradient with the momentum term:

m⁽ᵗ⁺¹⁾ ← α m⁽ᵗ⁾ − η ∇L(θ⁽ᵗ⁾ + α m⁽ᵗ⁾)
θ⁽ᵗ⁺¹⁾ ← θ⁽ᵗ⁾ + m⁽ᵗ⁺¹⁾

Since D is where the momentum is about to carry the parameters anyway, the gradient at D points towards the minimum better than the gradient at the current point A does.

One Learning Rate Doesn't Fit a Steep, Narrow Valley

Momentum addresses the direction and speed of a single combined step, but a separate problem shows up when the loss surface is much steeper in one direction than another -- an elongated valley, with contour lines like nested ellipses:

   ______________________
  (    ___________________)
  (   (        *          ))    ← steep left-right,
  (   (___________________))       shallow up-down
  (______________________)

With a surface like that, no single learning rate η can satisfy both requirements we care about: making good progress in both directions, and staying stable.

  • Choose η to suit the steep direction and training is stable, but very slow along the shallow direction, since the gradient there is much smaller.
  • Choose η to suit the shallow direction and the steep direction becomes very unstable -- the update zigzags back and forth across the valley instead of moving down it.

AdaGrad's fix is to scale each coordinate by how large its gradients have been. It keeps a running average of the squared gradient, s, and divides the gradient by (roughly) its own square root before taking the step:

s⁽ᵗ⁺¹⁾ ← β s⁽ᵗ⁾ + (1 − β) ∇L(θ⁽ᵗ⁾) ⊙ ∇L(θ⁽ᵗ⁾)      ← pointwise product
θ⁽ᵗ⁺¹⁾ ← θ⁽ᵗ⁾ − η ∇L(θ⁽ᵗ⁾) ⊘ √(s⁽ᵗ⁺¹⁾ + ε)          ← pointwise division

This scales both directions so the update moves about the same distance along each axis, instead of zigzagging along the steep one:

zigzag without scaling:          scaled, moves down the valley:
  \    /\    /\                        ↗
   \  /  \  /  \                      ↗
    \/    \/    \                    ↗
                                     ↗

But this comes with a cost. Because the scaling only cares about direction and is agnostic to the actual size of the gradient, AdaGrad does not converge to the exact minimum -- it oscillates around it. Near the minimum the gradient shrinks, which should be the signal to slow down, but after dividing by √s the step size stays roughly the same, so the optimizer keeps taking steps of a similar size and never settles:

        ____
       /    \
      |  *   |   ← oscillates around the minimum,
       \____/       step size doesn't shrink

Adam: Combining Momentum and AdaGrad

Adam combines the two, plus a bias correction for the moving averages:

1.  m⁽ᵗ⁺¹⁾ ← β₁ m⁽ᵗ⁾ − (1 − β₁) ∇L(θ⁽ᵗ⁾)                 ← momentum
2.  s⁽ᵗ⁺¹⁾ ← β₂ s⁽ᵗ⁾ + (1 − β₂) ∇L(θ⁽ᵗ⁾) ⊙ ∇L(θ⁽ᵗ⁾)       ← adaptive learning rate
3.  m̂⁽ᵗ⁺¹⁾ ← m⁽ᵗ⁺¹⁾ / (1 − β₁ᵗ⁺¹)   ┐
4.  ŝ⁽ᵗ⁺¹⁾ ← s⁽ᵗ⁺¹⁾ / (1 − β₂ᵗ⁺¹)   ┘  bias correction
5.  θ⁽ᵗ⁺¹⁾ ← θ⁽ᵗ⁾ + η m̂⁽ᵗ⁺¹⁾ ⊘ √(ŝ⁽ᵗ⁺¹⁾ + ε)

Step 1 is momentum. Step 2 is the AdaGrad-style adaptive learning rate. Notably, step 1 also helps step 2 converge: the momentum average of the gradient shrinks near the minimum (unlike the squared-magnitude average s), so combining the two counteracts the oscillation problem AdaGrad has on its own.

Steps 3 and 4 are the bias correction. Because m and s are both initialized at 0, the moving averages are biased towards 0 in the early iterations. Dividing by 1 − βᵗ corrects for this.

Step 5 is the update itself: move in the direction given by the bias-corrected momentum, scaled coordinate-wise by the bias-corrected second moment.

Adam, then, is not one idea but three: velocity (momentum), per-coordinate scaling (AdaGrad), and a correction for how the moving averages start at zero. Each addresses a specific, visualizable failure mode of plain SGD.

The learning rate η in step 5 multiplies the whole update, which is also exactly where things go wrong if you add ordinary L2 weight decay to Adam. That problem, and why AdamW exists, is covered in Adam and AdamW.

Summary

  • Plain SGD moves opposite the batch gradient; it's noisy, one learning rate has to serve every direction, and it can get stuck in shallow dips.
  • Momentum keeps a running velocity instead of using the gradient directly. Under a constant gradient it accelerates towards −ηg/(1 − α) -- 10× the plain step at α = 0.9 -- and it averages away batch-to-batch noise.
  • Nesterov Accelerated Gradient takes the gradient at the point momentum is about to reach, not at the current point, since the momentum vector already points roughly towards the minimum.
  • AdaGrad divides each coordinate's gradient by a running average of its own squared magnitude, so a valley that's steep in one direction and shallow in another gets one effective learning rate per direction. The cost: it becomes agnostic to the true gradient magnitude near the minimum, so it oscillates instead of settling.
  • Adam combines momentum and AdaGrad's per-coordinate scaling, plus bias correction for both moving averages since they start at zero. The momentum term also helps counteract AdaGrad's oscillation near the minimum.
